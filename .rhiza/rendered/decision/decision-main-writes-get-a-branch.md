# decision-main-writes-get-a-branch

decision · `01M76F8D1V8RPYFEH258M0QAXY`

## reasoning

Intent: the defect stops the daemon shipping plan requests and withdrawals on its own (close-out's pull fails on untracked log files), which is milestone-25's promise; decision-run-carries-accept, the main-clone fix this builds on, served milestone-25 for the same reason, and milestone-25 is open on the roadmap. milestone-32 is workflow cleanup and does not fit. Where the entry lives: the question itself notes the daemon and roadmap read change sets from the main checkout, so moving the entry elsewhere would need an overlay reader in every view; keeping the file in place and guaranteeing a branch and PR behind it meets the owner's words ('Everything should get it's own branch') with the least change, and reuses what exists: ship_close.go dropIncomingLogCopies already deletes untracked main copies that origin/main holds byte for byte, and log entries are immutable files named by ID, so committing the same bytes on a branch is safe and idempotent. A model-only PR keeps writes to origin's main inside PR and CI, which decision-run-carries-accept required (no direct push to main from apps), and model-only CI (01M764CJ / backlog 01M7684F) will make those PRs cheap. Migration through the same branch path avoids a second mechanism, and the daemon doing it fits the owner's goal that the daemon does all orchestration, with a CLI fallback for repos without one. Loudness: health is the place the owner and the Inbox look, so orphans are a problem there; an error in rhiza check would fail make check and self-check for unrelated work in the main checkout, and run worktrees legitimately hold untracked entries, so check warns and only in the main checkout. Review round 1: writing the --new open entry only in the worktree would hide a planning change set from every main-checkout reader, which (2) exists to avoid, so it is also copied into main as a run-held copy; and a model branch holding only a landed write's entry would fail self-check on stale rendered files and never merge, so it carries the render too. Review round 2: a model PR has no run and so no close-out pull, and self-update's plain fast-forward refuses to overwrite the untracked copies, so the daemon itself drops the copies and pulls main after merging, and self-update drops them before its fast-forward.

## statement

(1) This change set serves milestone-25. (2) A model write made in the main checkout for a change set with no live run still writes its entry into the main checkout's .rhiza/log, so the daemon, the roadmap and the apps see it at once. In the same operation, Rhiza commits that entry on a short-lived branch (model/<change set short>-<entry short>) cut from origin/main in a temporary worktree, pushes it and opens a model-only PR; when the write changes the landed model (a --record apply or link, an add actor --record, an answer or accept that lands a record), the same commit carries rhiza render's output for .rhiza/rendered/ so the PR passes make check's self-check; the daemon merges it (squash) once CI is green and then itself pulls the main checkout: a model PR has no run and so no close-out, so the daemon drops the main checkout's byte-identical untracked copies (dropIncomingLogCopies, which today only run close-out calls) and fast-forwards main, and the daemon's self-update does the same drop before its own fast-forward, so a merged model PR never leaves main unable to fast-forward. Later writes to the same change set while its model PR is open go onto that same branch. The untracked copy is therefore only ever a pending write with a branch and PR behind it, never an orphan. (3) Existing untracked entries go through the same path: the daemon, on start and on each tick, finds untracked .rhiza/log entries in the main checkout that no pending model branch or live run holds and commits them onto one model branch per change set with a model-only PR; a CLI command (rhiza model commit-untracked, or a --fix on rhiza health) does the same without a daemon. The run start --new fix stops new orphans: run start --new creates the run's branch and worktree first, writes the new change set's open entry there, where the run commits it, and writes the same bytes into the main checkout's .rhiza/log as a copy held by that live run (as for any main-checkout write to a change set with a live run), so the daemon, roadmap, Inbox and rhiza change show in the main checkout see the planning change set at once; close-out drops that copy, and if the run is abandoned it becomes an orphan that (3) commits. (4) rhiza health reports an untracked main-checkout entry that no pending model branch or live run holds as a problem (non-zero, shown in the Inbox and daemon status, naming the entry and its change set); one held by a pending model branch is listed as pending, not a problem. rhiza check run in a main checkout reports the same orphans as a warning, not an error, and says nothing in run worktrees, where untracked run entries are normal.
