## reasoning

Intent: the sibling change sets carved out of accepted umbrellas this session (code anchors 01M6HJX, unclaimed changes 01M6HKR) both serve model-tells-truth, and text-references' own statement (a rename never breaks a sentence) is about the model staying true; anyone-builds is the umbrella's broader root and adds nothing here. The carving guide says carve keeps IDs and links and that an emptied source is withdrawn by hand, and references-by-id is landed so the decided-by link applies in the target. Stored form: references-by-id says stored by ID, shown by handle; a bracketed @@{ID} cannot collide with the '@' already in the log (emails, checkout@v7, '@key'), and requiring whitespace or ( [ before @ keeps those three from being read as references even on new writes. Verbatim fields are skipped because the hard rule is never to alter an owner's exact words, and sources are scrubbed transcripts. Refusing an unresolvable reference mirrors how a link to a node the write may not see is refused, and keeps a dangling reference from ever being written; @@@ gives an escape so a literal @@word can still be written. Resolving an input @@{ID} like any reference, rather than passing it through as already-stored text, keeps a hand-typed @@{BOGUS} from being stored unrefused; re-escaping a literal @ as @@@ on display keeps a stored literal @@word from being read back as a reference. Showing by current handle in both text and JSON makes output round-trip through a later write. A missing node in check is a fail because the capability exists so sentences never break, while a retired target is still a real node, so only a warn. Only a full 26-character ID inside @@{ } counts as stored form because landed text, this plan's own included, already holds look-alikes such as '@{ID}' and '@{BOGUS}', and check must stay clean on it; such legacy text is shown with its @ re-escaped, which keeps the round trip. A retired target is shown by full ID, not handle, because Resolve matches handles only among live nodes, so a shown @<handle> would be refused or would silently bind to a live node that has since taken the handle; keeping an already-stored retired reference on write lets that shown text go back to its field. Every read operation that prints node text shows handles, not only the original five, because references-by-id says references are shown by handle without exception, and search over shown text keeps '@handle' searchable.

## statement

(1) Intent and leaf: the change set serves the landed root intent model-tells-truth, and the leaf comes over with rhiza carve text-references --from 01M5SWSWDVB237 --to 01M6HNNWFR1J2AHQRNKFTPME46, which keeps its ID and moves its decided-by link to references-by-id; the umbrella, left with no ops, is withdrawn. (2) Stored form and scanned fields: a write (node add or set) scans every string-valued field of a node, except the verbatim fields quote, quote_where and wording and every field of a source node, which are stored exactly as given. A reference starts with @ at the start of the text or after whitespace or an opening ( or [, followed by a handle (lower-case words joined by dashes), a node ID or unique ID prefix of 4+ characters, or the stored form {<full node ID>}; so emails, checkout@v7 and a quoted '@key' are not references. @@@ writes a literal @ and is never resolved. Each reference is stored as @@{<full node ID>}, and only @@{ followed by a full 26-character node ID and } counts as a stored reference; any other @@{...} in stored text (such as '@{ID}' or '@{BOGUS}' in prose) is literal text; an @@{<ID>} in a write's input is a reference like any other, resolved and refused by the same rule, so hand-typed stored form cannot bypass resolution; json_fields and links are not scanned. Already-landed entries are never rewritten; they hold no stored reference (no @@{<26-character ID>} is in the log today), and their literal @ that would start a reference is shown re-escaped (old '@word' as '@@word', '@{ID}' as '@@{ID}'), which written back stores the same literal text. (3) Unresolvable reference: the write is refused whole (not found, exit 4), naming each reference that names no node the write may refer to; the rule is the same as for a link's ends: landed nodes and nodes of the write's own change set, live and not retired, except that a reference to a retired node is kept when the field's current stored value already holds that same ID, so text that already refers to a node retired since is not refused when written back to its field. The error's next says to fix the handle or write @@@ for a literal @. (4) Display and check: every read operation that prints a node's text fields (render, show, why, slice, ls, tree, search, inbox, feed, roadmap, change show and change diff, the last two in the change set's view) and the read apps, text and --json alike, show each @@{ID} naming a live node as @<the node's current handle> in that view and re-escape as @@@ each stored literal @ that would otherwise start a reference, so the shown text written back to the same field in that view stores the same text; a reference to a retired node is shown as @@{<full ID>} (handles resolve only among live nodes, so @<handle> could not round-trip) and written back to its field is kept by rule (3); a reference that does not resolve in the view is shown as @@{<full ID>}, and writing that back is refused like any unresolvable reference. search matches its query against the shown text, so a search for '@other' finds a stored reference to other. rhiza check scans the folded model's stored references (@@{<26-character ID>} only), each in the view of the change set that wrote it: an ID that names no node is a fail finding (a dangling reference), naming the node, field and ID; an ID that names a retired node is a warn.
